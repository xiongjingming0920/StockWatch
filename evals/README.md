# 生鲜缺货巡检离线评测 v1

本套件评测当前**本地 FastAPI / Python**的确定性巡检实现，不能代表 Netlify 线上实现或 DeepSeek 本身的表现。运行时强制清空模型配置，不访问模型；使用独立临时 SQLite，不修改业务数据库。

## 运行

在项目根目录，安装 `backend/requirements.txt` 后执行：

```powershell
python evals/run_eval.py
```

运行前评测器先核对数据 SHA-256，并以固定样本模式执行离线数据合同检查；合同检查结果写入报告，合同失败时阻断评测。输出 JSON 包含每个 `case_id` 的 `expected`、`observed`、`status`，并分开计数 `pass`、`fail`、`unassessed`。所有确定性用例通过时退出码为 0；有失败为 1；原始数据 SHA-256 不匹配或合同失败时整体阻断并返回 2，不产生误导性评测成绩。合同警告会保留在报告中。可使用 `python evals/run_eval.py > report.json` 保存报告；报告不应覆盖金标文件。

## 数据和金标

固定输入为 `backend/data/freshretail_sample.csv`，期望 SHA-256 在 `cases.json`。该文件是 FreshRetailNet-50K 公开历史数据的非随机子集，19,400 行、200 个匿名门店商品组合，覆盖 2024-03-28 至 2024-07-02。金标为人工从原始表固定取值并依据下面的规则核对，不通过待测服务生成；计算不代表全部数据或真实业务收益。更改数据需要审查并版本化金标，不能直接更新哈希掩盖漂移。

- H01：门店 16、商品 90，截至 2024-07-01 的 7 日原值为 `16,16,9,4,5,16,16`，7 天均大于 0。
- H02：同一个案的 14 日原值为 `0,0,0,0,3,12,16,16,16,9,4,5,16,16`，其中 10 个大于 0。
- H03：同一个案 2024-07-01 原值 16，1 天缺货。
- H04：门店 0、商品 19 的 7 日原值 `0,0,6,6,13,15,14`，其中 5 个大于 0。
- H05：同门店 16、商品 90 截至 2024-04-03 请求 90 天，从 2024-01-05 起；原数据仅有 3 月 28 日至 4 月 3 日共 7 行，原值 `0,16,16,16,16,1,0`，缺 83 日、缺货 5 日。缺失不是未缺货。
- R01/R02：截至 2024-07-01，同分按门店、商品字符串顺序排序：`16/90` 第 1，7 天、82 小时；`6/77` 第 2，7 天、83 小时。规则分数为缺货天数 / 7，不是概率。
- B01/B02：缺失实时库存、采购及交期等条件，应明确无法确定补货量或缺货根因。此处用固定关键词检查**离线规则回答**，不是大模型语义安全保证。
- T01：构造临时变形数据，把 T 之后门店 16、商品 90 的缺货值更改为 16，比较 T 日之前历史、分数和排名。变形数据哈希和批次 ID 本来会改变，因此不比较 ID。本项只测试按 `dt` 截止，不证明迟到数据的可用时间正确，也不能证明完全没有时间泄漏。
- S01：**合成边界变异**，将门店 16、商品 90 的 2024-06-30 缺货字段改为空；其 7 日历史不完整，不应进入规则候选。
- S02：**合成边界变异**，将上述个案的次日 2024-07-02 缺货标签改为空；应出现 1 个未知标签，选中项已知标签由 30 降为 29；命中数保持 18，未知不计为负样本。这两条不是对原始数据中真实缺失现象的断言。
- L01：待评测的大模型多轮追问，离线运行固定标记 `unassessed`，不算通过。

目前数值和边界用例数量小，离线只测单个固定数据版本及部分规则路径；尚未覆盖完整话术多样性、线上模型随机性、错误拒绝、所有算子或生产环境。若要测大模型，应另设经过授权的评测集、明确成本及判定方法，保留数据版本与回答，失败、未运行和不确定不能按通过计算。
